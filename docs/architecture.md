# 项目架构

## 三层职责

1. **访谈控制**：`HumanInterview` 把开场、播报、监听、思考、收尾与保存组织成状态机。收到真实 ASR 之前不会推进问题树。
2. **文字决策**：`VoiceTree` 在当前问题播报 / 等待回答期间预生成候选，记录当时上下文指纹。回答到达后由 Qwen 选择候选；候选过期、不适配或尚未就绪时重新生成。证据引用必须来自已有受访者原话。
3. **语音与系统设备**：MOSS-Live 负责语音输入转写，MOSS TTS 合成控制器确定的提问；Swift / WASAPI 音频桥负责麦克风、连续播放和本机录音。

“模型提前准备问题”与“模型知道未来回答”不同。候选只能使用已经发生的对话及研究目标，未选分支没有受访者回答。候选命中仍需要选路推理，所以并非零延迟。

## 与端到端语音模型的关系

MOSS-Live 能在一个实时语音会话中理解语音并生成回复。本项目将语音和业务选路分开，是为了让提问可以校验、记录和复盘：实际说出口的问题由树控制器确定，不能由语音角色自由追加。MOSS-Live 监听会话的自动语音回复不进入采访员播放链路。

这种组织方式牺牲了部分端到端自由度，并增加了识别到文字决策、再到合成的调用阶段。优点是能够检查每次用到了哪条原话、为什么选这个问题、是否重复或引用了不存在的证据。

## 当前时序

```text
Qwen 开场 JSON → 校验 → MOSS TTS 流式 PCM → 系统播放
                         同时准备下一轮候选
系统播放结束 → 允许提交真人麦克风输入
语音停止 + 已收到最终转写 → 停顿窗口 → 使用当时的 ASR
Qwen 选路 / 重新生成 → 校验 → 下一问
达到轮次 / 结束口令 → 停止设备 → 对齐录音 → 写文稿与树 → ZIP
```

模型 JSON 完整返回并通过校验后才提交 TTS；TTS 音频分块接收、排队播放，不等待整段合成完成。录音采用连续设备音频时钟，不用网络包抵达时间拼出对话。

## 识别修订与决策证据

`input.transcript.updated / done / revised` 原样逐条保存。决策使用的版本固定在提交当时，后到的修订不会改写已经作出的决定。每轮绑定 ASR 事件 ID、实际使用文本、模型调用 ID、候选与下一问。

## 尚未完成的全双工能力

当前采访员说话时不提交麦克风给识别服务，因此不能边播报边理解打断。后续需要：持续监听、回声消除、用户打断判定、停止旧播放、取消旧生成、依据已实际播放内容更新树，以及重叠音频的事件关联。底层服务支持双向流，并不能证明这些应用行为已经完成。
