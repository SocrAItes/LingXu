# 项目架构

## 三层职责

1. **访谈控制**：`HumanInterview` 把开场、播报、监听、思考、收尾与保存组织成状态机。收到真实 ASR 之前不会推进问题树。
2. **文字决策**：`VoiceTree` 在当前问题播报 / 等待回答期间预生成候选及其适用条件，记录当时上下文指纹。回答到达后由 Qwen 返回候选编号，或者在同一次调用中生成新问题。明确纠正、换话题、拒答或不确定会停用旧候选，这些检查只使候选失效，不替模型选问题。候选尚未准备好时取消准备请求，直接生成，不继续等待。
3. **语音与系统设备**：MOSS-Live 负责语音输入转写，MOSS TTS 合成控制器确定的提问；Swift / WASAPI 音频桥负责麦克风、连续播放和本机录音。

“模型提前准备问题”与“模型知道未来回答”不同。候选只能使用已经发生的对话及研究目标，未选分支没有受访者回答。候选命中仍需要选路推理，所以并非零延迟。

## 与端到端语音模型的关系

MOSS-Live 能在一个实时语音会话中理解语音并生成回复。本项目将语音和业务选路分开，是为了让提问可以校验、记录和复盘：实际说出口的问题由树控制器确定，不能由语音角色自由追加。MOSS-Live 监听会话的自动语音回复不进入采访员播放链路。

这种组织方式增加了识别到文字决策、再到合成的调用阶段。可以检查每次实际输入了哪条回答、模型返回了哪个候选或新问题，以及是否重复。模型返回的短决策不代表完整内部推理。

## 当前时序

```text
Qwen 开场 JSON → 校验 → MOSS TTS 流式 PCM → 系统播放
                         同时准备下一轮候选
系统播放结束 → 允许提交真人麦克风输入
语音停止 + 已收到最终转写 → 停顿窗口 → 使用当时的 ASR
Qwen 短选路 / 同次生成新问题 → 校验 → 下一问
达到轮次 / 结束口令 → 停止设备 → 对齐录音 → 写文稿与树 → ZIP
```

模型 JSON 完整返回并通过校验后才提交 TTS；TTS 音频分块接收、排队播放，不等待整段合成完成。录音采用连续设备音频时钟，不用网络包抵达时间拼出对话。

## 识别修订与决策证据

`input.transcript.updated / done / revised` 原样逐条保存。决策使用的版本固定在提交当时，后到的修订不会改写已经作出的决定。每轮绑定 ASR 事件 ID、实际使用文本、模型调用 ID、候选与下一问。

紧凑选路先摘出本轮回答中的短原话 `anchor`，再返回候选编号 `pick`。程序检查短原话确实来自本轮回答，并用当前回答的已知 ID 关联，不让模型生成引用编号。需要新问题时直接返回 `pick=new` 与问题 `text`，收尾使用 `pick=finish`。`decision` 保留模型原始 JSON。`input_provenance` 和 `input_turn_ids` 是程序对实际输入的关联，明确标记为应用来源。`reason_source=application` 的文字仅说明处理结果，不声称是模型当时的理由。开场、收尾及受保护的研究政策流程仍校验其原话引用。

明确纠正、切换对象、换话题或负面重估时停用旧候选，并只向选路器提供当前问题和本轮回答，避免旧经历持续牵引。完整历史仍保留在树与日志中，程序仍用完整历史检查逐字重复。这个保守策略可能放弃部分原本可用的缓存，不保证语义重复或所有访谈质量问题已经解决。

用户有明确转折表达时，`current_focus_quote` 保留其转折后的逐字原话，并标记为程序提取的输入提示，不作为新的用户发言或模型理由。如果恢复输出只遗漏 `pick=new`，但已经给出完整问题、合法话题且候选已停用，程序显式记录字段补齐，原始 `decision` 不变。连续无效结构转入独立现场生成，不强行套用旧候选。

## 尚未完成的全双工能力

当前采访员说话时不提交麦克风给识别服务，因此不能边播报边理解打断。后续需要：持续监听、回声消除、用户打断判定、停止旧播放、取消旧生成、依据已实际播放内容更新树，以及重叠音频的事件关联。底层服务支持双向流，并不能证明这些应用行为已经完成。
